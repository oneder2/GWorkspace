# 两馆连续展厅与 Spotify 修复记录

日期：2026-10-02。状态：已恢复在线验证和发布，最终发布记录见文末。原有首页、数学背景、伪终端等无关的未提交修改保留在工作区，没有带入发布。

## 调研与空间判断

完整调研和概念平面见 [两馆紧凑空间重设计提案](COMPACT_GALLERY_PROPOSAL.md)。参考 Louvre-Lens 的连续展场、MASP 的独立展架与自由观看路线、Louisiana 的短环路和景观转场。借鉴组织原则，不沿用实体博物馆的大空间尺寸。

原问题来自分类与房间一一对应、纵向串联、固定连接段，以及只渲染当前房间展品。主题标签不应直接决定建筑边界。改用连续外壳、三个开放展区、横向通道与中部捷径。

## 阶段一：布局和碰撞

- 造物工坊和星图阅览厅使用同一有限容量的开放厅模板，保留不同排列、材料和展具；林地继续使用原有专用场景。
- 每批最多 12 件。超出时出现“参观下一组展出”，目录仍按现有 API 每批最多 8 件取回，不删除或隐藏收藏。
- 9 / 12 件配置的外壳为 18.8 × 21.6 = 406.08 场景单位²。相较调研快照约 1,216 / 1,939 的面积，分别减少约 67% / 79%。场景单位不是现实米。实际首批数量由公开 API 决定，本次本地数据副本返回工坊 9 件、阅览厅 8 件，12 件容量另有自动化测试。
- 小批次按实际占用行数缩短地面；摘要字数不参与面积计算。
- 使用现有模型族的保守占地包络 2.6 × 2.6，加上玩家半径 0.35。中部物理净宽 2.8；每件保留距中心 2.45 的观看点。没有缩小原有模型比例。
- 主题相近的作品优先相邻；重点作品优先分配。阅读量和模型版本不会改变展位。
- 优先以数据库模型 ID 保存同一浏览器、同一展出批次的展位；修改项目 slug 不会搬动作品，同一模型重复展出时用独立展品 ID 区分。兼容迁移早期浏览器展品 ID 键。已有作品保留位置，新作品填空。布局版本键用于后续显式重新策展。

这是受约束的模板分配，尚不是自动测量任意模型包围盒的布局求解器。当前模型族使用已有固定尺寸；新增更大的模型族时需先调整包络和通行测试。浏览器存储不等于跨设备、后台统一策展的数据库记录，后者仍是后续能力。

## 阶段二：建筑、展具、镜头和交互

- 全批次模型同时挂载，不再仅显示当前展区。实时展品聚光灯限制为当前展区最多四盏，公共主光不随展区跳动。
- 工坊：冷灰连续地面、铜色收边、错位的金属展岛、远侧构件背衬。
- 阅览厅：靛蓝阅读区、暖木与纸色背衬、浅折线展位；阅读湾有独立短背衬，入口侧有一处停留坐凳。短背衬与坐凳同时进入碰撞数据，薄背衬碰撞按玩家进入的一侧处理，避免穿透或推出外墙。赠语使用独立浮页窗框，不再占一间房。
- 连续远墙与两侧外轮廓形成完整建筑；高位边框替代不透明整片屋顶，入口侧保留剖切视野。
- 近看镜头从观看点一侧进入，遮挡检查扩大为多条视线；密集展品选择加入移动方向、前方展台遮挡判断与切换滞后。
- 保留独立内容模型、完整展签、项目链接、文章正文入口、参观指南和收藏目录。

- Gellaria ESLint、TypeScript 检查通过。
- GWorkspace Vite 生产构建通过。
- 恢复环境权限后，最终工作树的默认 Turbopack 生产构建通过；独立发布工作区的 GWorkspace Vite 构建和体积检查通过。
- 真实浏览器首次验收发现首屏布局的 hydration 错误：服务端和浏览器排序环境不同，且浏览器会立即恢复本地展位。已改为确定性的字符排序，并在 hydration 后恢复展位。复验默认加载和保存非默认展位后的刷新均未再出现该错误。

浏览器证据保存在本地 `output/playwright/compact-*.png`。自动化路径检查覆盖全部观看点；浏览器检查补充真实 WebGL、交互与遮挡证据，不声称已覆盖所有硬件和相机角度。

## Spotify

发现并修复的代码缺陷：访问令牌遭 401 拒绝后不重试、并发重复刷新、上游请求没有超时、429 没有等待、前端曲目链接漏读 `externalUrl`、未知进度变成零、请求失败被显示为“此刻安静”、卸载时请求未取消。

后端增加共享刷新与播放请求、10 秒短缓存、一次 401 刷新重试、单次上游请求 3.5 秒超时、跨 market 的 Retry-After 等待，保留曲目响应字段并支持播客。204 和错误同样返回 `Cache-Control: no-store`。后台状态区分未验证、可用、空闲、失效和陈旧状态。

续轮复查补上重新授权与在途请求之间的竞态保护：旧的刷新结果不覆盖新连接凭据，旧播放和限流结果不能重新填入已清空的缓存。测试模拟了新授权完成后旧响应才返回的顺序，验证数据库、公开播放结果和连接状态均保留新连接。

前端使用完成后再调度的轮询，15 秒请求上限，后台标签页暂停轮询、恢复后重查，卸载时取消请求，单独展示失败状态。

入口：站长后台 → 系统管理 → Spotify 集成状态 → “检查播放连接”。如果提示授权失效，再点原授权按钮。授权现由管理员请求一次性跳转票据，在 API 域名设置 OAuth cookie；回调校验服务端一次性 state，刷新凭据只保存在后台，不再返回到页面。刷新凭据无法写入数据库时不报告成功。旧的公开 `/api/spotify/login` 裸链接现在提示从管理页发起。

验证命令：`npm run check:spotify`、`npm run check:spotify-widget`。前者使用临时数据库和模拟 Spotify 响应，直接执行 Express 路由及权限中间件，不监听端口；后者有 4 项前端轮询/数据测试。覆盖刷新合并、401、凭据轮换持久化、204、播客、invalid_grant、403、超时、429、缓存头、管理员入口、一次性 state 和凭据不回传。

浏览器补充验证了模拟曲目、204 空闲、503 失败，以及临时数据库管理员的“检查播放连接”和带认证的授权 POST。模拟失败产生的 HTTP 错误属于预期测试结果。没有变更生产 Spotify 凭据或控制账户播放；生产空闲响应不等于实际音乐播放验收。
